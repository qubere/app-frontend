# TMS-03: Agent/Autonomy Health Audit — apps/tms

Audited: uncommitted local changes in `apps/tms`, `packages/assistant`, `packages/decisions`, `packages/auth`, `packages/db/prisma/schema.prisma` against `docs/plans/AI-FREIGHT-EXECUTION-WORKFLOW.md`.

**Bottom line verdict:** apps/tms is a real, fairly substantial Next.js app with genuine deterministic business logic (rate scoring, 3-way invoice matching, LFD/demurrage risk math, a real per-account autonomy-policy gate). But the specific claim this audit was asked to test — "agentic" in the sense of AI-driven understanding and autonomous execution — is **largely fake**. There is no LLM/AI SDK call anywhere in the app. The chat "AI assistant" is a hardcoded keyword router. The "AI document parsing" endpoint and its UI panel return identical hardcoded fabricated data for every document. The "AI email intake simulator" never parses anything — it persists whatever `confidence`/`evidenceItems` the caller supplies, and the UI that's wired to it supplies neither, so every submission silently gets a hardcoded 85% confidence and zero evidence. Two tracking-integration files fabricate named-vendor telemetry (fake driver name, fake phone number, fake AIS position) though they are currently unwired to any UI. On top of the "no LLM" problem, several mutation routes bypass auth/tenant-scoping entirely, which is a separate, serious correctness issue.

The one genuinely good piece of engineering here is `apps/tms/src/modules/autonomy/services/policyEngineService.ts` — a real, config-driven autonomy gate that 4 different agent modules actually call before writing to the DB. But even that is only half-wired: 4 of the 6 new `AgentPolicyConfig` TMS fields are loaded from the DB and then never checked by anything.

## P0 — the "agentic" story is fake or misleading for a demo

### P0-1: Zero real LLM/AI SDK calls anywhere in apps/tms or packages/assistant
**CONFIRMED.** Repo-wide grep for `anthropic|openai|Anthropic|OpenAI|generateText|messages.create|@ai-sdk` across `apps/tms/src` and `packages/assistant` returns zero matches. `apps/tms/package.json` has no `@anthropic-ai/sdk`, `openai`, or `ai` package dependency at all. `apps/tms/.env.local` has no `ANTHROPIC_API_KEY`/`OPENAI_API_KEY`. For contrast, `apps/custom/src` has 5 files that do call the Anthropic SDK (e.g. `apps/custom/src/modules/assistant/orchestrator.ts`, `apps/custom/src/lib/audit/focusedAssessment.ts`). apps/tms was built with no equivalent capability at all.

### P0-2: The "AI assistant" chat is a hardcoded keyword router, not an LLM
**CONFIRMED**, `apps/tms/src/modules/assistant/orchestrator.ts:13-112`. `runAssistantTurn` does `const msg = turn.message.toLowerCase()` and then a chain of `if (msg.includes("sweep risk") ...) ... else if (msg.includes("freight audit") ...) ... else if (msg.includes("shipment") ...) ...` etc., each branch invoking one fixed tool and returning a fixed markdown template. There is no tool-calling loop, no LLM turn, no free-form understanding — it is a string-match dispatcher. The fallback branch (line 98-108) literally introduces itself as "I am your **Qubere AI Freight & Transportation Supervisor**" while being incapable of understanding anything outside ~6 hardcoded phrases.

Compounding this: `apps/tms/src/app/api/assistant/chat/route.ts:1-33` has no auth check at all, and calls `runAssistantTurn("Enterprise Freight", { message, history }, )` **without a third `ctx` argument**. `orchestrator.ts:21` then falls back to `const serviceCtx = ctx ?? { accountId: "acc_tms_01" }` — a hardcoded literal account id. Every chat session, from any signed-in tenant, operates against this one hardcoded fake account. This isn't just "not agentic," it's not even tenant-aware.

### P0-3: "AI document parsing" is 100% fabricated, both server- and client-side
**CONFIRMED.** `apps/tms/src/app/api/documents/[id]/parse/route.ts:11-41` builds a literal `mockExtractedFields` array (fake "Importer of Record: Acme Import Logistics LLC", fake ports, fake container number, confidence values 99/97/99/95 hardcoded) and returns it as the parse result for **any** document id, without ever reading the document's actual content. The response even says `message: "AI Agent completed 100% OCR parsing and bounding box extraction."` — an explicit, false claim of work performed.

Independently, `apps/tms/src/components/DocumentReviewPanel.tsx:44-79` hardcodes the *exact same* fake fields (`extractedFields: ProvenanceField[] = [...]`) directly in the React component, so the "Document Provenance" review panel (with a Sparkles/AI icon) shows identical fabricated extraction data for every document a user opens, independent of whichever API call may or may not have run. This is precisely the failure mode Section 3 Rule 1 of the spec was written to prevent ("never invent a plausible value") — it happened anyway, in the most visible part of the product (a document review screen a customer would look at).

### P0-4: "AI Email Intake" never parses anything; UI mislabels itself "Real-Time NLP Parsing"
**CONFIRMED.** `apps/tms/src/app/orders/page.tsx:47-83` renders an "AI Email & Document Intake Simulator" card badged **"Real-Time NLP Parsing"**, with copy claiming the button "Triggers evidence provenance extraction, confidence scoring, and AgentDecision classification." The form is a plain HTML `<form action="/api/transportation-orders/parse" method="POST">` with a single `<textarea name="text">` field — no JS, no fetch, no LLM call of any kind on the client.

The target route, `apps/tms/src/app/api/transportation-orders/parse/route.ts:21-33`, forwards `body.confidence` and `body.evidenceItems` straight through to `parseIntakeRequest` — i.e. it expects the *caller* to already have done the extraction and to supply confidence/evidence as input. Since the UI form only submits a field named `text` (route expects `rawText` — a field-name mismatch, so `rawText` is also `undefined` in every submission from this UI) and never supplies `confidence` or `evidenceItems`, every order created through this "AI simulator" gets:
- `apps/tms/src/modules/orders/services/intakeParserService.ts:39`: `const confidence = input.confidence ?? 85;` — hardcoded fallback, no real scoring.
- Line 40: `const isHighConfidence = confidence >= 80;` — a **hardcoded threshold**, not `AgentPolicyConfig.autoThreshold`, directly contradicting the spec's explicit instruction ("reuse `AgentPolicyConfig`, don't hardcode a threshold" — Phase 1) and the validation checklist item about hardcoded confidence.
- `evidenceItems: (input.evidenceItems ?? []) as any` — empty evidence array, contradicting Section 3 Rule 4 ("Every AI-produced record carries evidence... not optional decoration").

The same hardcoded-80 pattern is duplicated in the `AssistantTool` version of this flow: `apps/tms/src/modules/orders/tools/parseFreightEmailTool.ts:55`: `const autoThreshold = 80;`.

### P0-5: Fabricated named-vendor "live tracking" data (currently unwired, but a landmine)
**CONFIRMED**, dead/unwired but present in the tree. `apps/tms/src/modules/tracking/services/oceanTrackingService.ts:31-67`, function `fetchLiveOceanTracking`, builds a `mockPosition` object (its own variable name admits it) with a hardcoded vessel name, MMSI `351829000`, IMO `9820192`, lat/long, heading, speed, and `lastReportedIso` computed as "2 minutes ago" to look live — then returns it labeled `sourceProvider: "Project44 AIS Telematics (Satellite Stream)"`, falsely attributing fabricated data to a specific real third-party vendor.

`apps/tms/src/modules/tracking/services/drayageTelematicsService.ts:24-46`, function `fetchDrayageTelematics`, is worse: it fabricates a named human driver (`"Marcus Vance"`), a fake phone number (`"+1 (415) 892-0192"`), fake truck/chassis numbers, fake GPS coordinates, and labels the source `telematicsProvider: "Samsara ELD Integration"` — again a false attribution to a real named vendor.

Neither function has any caller anywhere in `apps/tms/src` (confirmed via repo-wide grep — only self-references in their own file) and neither is imported into any route or page, so today this data is not shown to a user. The real shipment workspace (`apps/tms/src/modules/shipments/services/shipmentWorkspaceService.ts:93-94,157-215`) correctly reads live `TrackingEvent`/`EtaObservation` rows from the DB. But these two files exist in the tree, compile, and are named so plausibly ("fetchLiveOceanTracking") that a future change (or another AI coding pass) is one `import` away from wiring fabricated data into the live product under a real vendor's name. Given the spec's own stated history of this exact tool fabricating data on a prior task in this repo, this should be deleted, not left as a trap.

### P0-6: Several mutation/query routes bypass auth and tenant-scoping entirely
**CONFIRMED**, multiple distinct bugs:

- `apps/tms/src/app/api/transportation-orders/parse/route.ts:6-19` — does not use `withAuthenticatedRoute`. It manually calls Clerk's `auth()` for a userId, then builds `const mockCtx: any = { userId, accountId }` where `accountId = body.accountId ?? "acc_default"` — **the tenant id is taken directly from the untrusted request body**, with no `AccountMembership` check. Any authenticated user can write a `TransportationOrder` into any tenant's account by passing a different `accountId` in the JSON body. This is a direct violation of Section 3 Rule 3 ("No handler should manually re-derive `accountId`... or hand-roll a permission check") and the spec's validation checklist ("Every new mutation route uses `withAuthenticatedRoute`"). The variable is even named `mockCtx`.
- `apps/tms/src/app/api/orders/ingest/route.ts:1-16` — no auth check of any kind (no Clerk `auth()`, no `withAuthenticatedRoute`). Anyone can POST and create records via `ingestErpPurchaseOrder`.
- `apps/tms/src/app/api/shipments/route.ts:1-30` (GET) — no auth check and **no `accountId` filter in the Prisma query at all** (`db.shipment.findMany({ where, ... })` where `where` only ever contains `mode`/`status`). This returns up to 50 shipments, including `customsFilings` and `exceptionItems`, across every tenant in the database, to any unauthenticated caller. This is a cross-tenant data leak, not just a missing-permission gap.
- `apps/tms/src/app/api/webhooks/tracking/route.ts:18-72` — no auth, no signature verification (contradicts the spec's explicit instruction to reuse the Resend inbound-email webhook's signature-verified pattern, Phase 5). It also does `db.shipment.findUnique({ where: { id: parsed.shipmentId } })` with **no `accountId` scoping**, so anyone who knows or guesses a `shipmentId` belonging to a different tenant can inject fabricated `TrackingEvent`/`EtaObservation` rows into that tenant's shipment timeline (cross-tenant IDOR), which then feeds real exception detection and the risk agent.
- `apps/tms/src/app/api/customs/webhook/route.ts:7-16` — same pattern: no auth, no signature check, and takes `accountId` straight out of the request body.
- `apps/tms/src/app/api/carriers/route.ts:1-11` (GET) — no auth, and returns a **fully hardcoded static array of 3 fake carriers** ("Western Freight Logistics" DOT 289104, "Swift Freight Lines," "Knight Transportation" with invented OTD scores) instead of querying the DB. Confirmed via grep this route is referenced only from `apps/tms/src/app/admin/integrations/api-docs/page.tsx` (self-documentation), not from the live Carriers page (`apps/tms/src/app/carriers/page.tsx`, which correctly reads `db.carrierProfile`) or the chat's `list_carriers` tool (which correctly calls the real `evaluateCarriersForShipment`). So this is currently dead/orphaned rather than actively shown to users — but it is a real, reachable API endpoint returning fabricated data, and it's the one endpoint documented on the API-docs page as the carrier list, meaning an external integrator hitting the documented API would get fake data.

For contrast/positive finding: `apps/tms/src/app/api/exceptions/[id]/resolve/route.ts` **does** use `withAuthenticatedRoute(..., { permission: "exceptions.resolve", write: true })` correctly, and additionally gates high-impact actions with a second permission check — see P1 note below on why this one route is the exception, not the rule.

## P1 — partially implemented / inconsistent

### P1-1: 4 of the 6 new `AgentPolicyConfig` autonomy fields are loaded but never enforced
**CONFIRMED.** `apps/tms/src/modules/autonomy/services/policyEngineService.ts:105-187` (`evaluateAutonomyPolicy`) is real, well-structured, config-driven gating logic, and it is genuinely called from 4 separate agent modules (`apps/tms/src/modules/tenders/services/tenderService.ts:364`, `apps/tms/src/modules/rating/services/quoteService.ts:191`, `apps/tms/src/modules/invoices/services/freightAuditAgent.ts:58`, `apps/tms/src/modules/agents/services/operationalAgents.ts:119,230,386,397`). That part is real and is the strongest piece of evidence for genuine autonomy gating in this codebase.

However, of the 6 TMS-specific fields added to `AgentPolicyConfig` (`packages/db/prisma/schema.prisma:1237-1249`):
- `autonomyMode` — **enforced** (`policyEngineService.ts:119`, Gate 0: SUPERVISED always blocks).
- `financialThreshold` — **enforced** (`policyEngineService.ts:149-157`, Gate 3).
- `marginThreshold` — loaded into the policy object (`policyEngineService.ts:77`) but **never read anywhere else in the codebase** (confirmed via grep for `.marginThreshold` outside `policyEngineService.ts` — zero matches). `apps/tms/src/modules/rating/services/quoteService.ts:202-213` computes its own `targetMarginPct` from `input.targetMarginPercent ?? 15.0` and a separately hardcoded `0.8` tolerance multiplier, ignoring the account's configured `marginThreshold` entirely.
- `carrierApprovalRequired` — loaded (`policyEngineService.ts:78`), **never read anywhere else** (zero matches outside the file).
- `requireInsurance` — loaded (`policyEngineService.ts:79`), but every actual call site hardcodes `requireInsurance: true` as a literal instead of reading the loaded policy value: `apps/tms/src/modules/tenders/services/tenderService.ts:289,392`, `apps/tms/src/modules/rating/tools/recommendCarrierTool.ts:10` (Zod default), `apps/tms/src/modules/assistant/tools.ts:159`. The config field exists, is plumbed into a policy object, and is then ignored in favor of a literal `true` at every use site — an account that sets `requireInsurance: false` has no way to actually change agent behavior.
- `requireCustomsRelease` — loaded (`policyEngineService.ts:80`), **never read anywhere else** (zero matches outside the file). Spec's Phase 5 explicitly calls for gating drayage dispatch on this; no such gate exists.

Net effect: the schema and the loader make it *look* like all 6 fields are wired into real autonomy control, but only 2 of 6 (`autonomyMode`, `financialThreshold`) actually change agent behavior. This is worth flagging precisely because it's the kind of thing that would pass a shallow "grep for the field name, see it's used" check while still being non-functional for a customer who tries to configure it.

### P1-2: "Confidence" values fed into the policy gate are hardcoded magic numbers, not derived from anything
**CONFIRMED**, pattern repeats across every agent:
- `apps/tms/src/modules/agents/services/operationalAgents.ts:86,93`: `etaConfidence = 90` (no delay) or `82` (delay detected) — a binary flip, not a computed confidence.
- Same file, lines 232, 388, 399: `confidenceScore: 95`, `90.0`, `88` — fixed literals per branch.
- `apps/tms/src/modules/invoices/services/freightAuditAgent.ts:55`: `const confidence = isClean ? 96 : 60;`
- `apps/tms/src/modules/rating/tools/recommendCarrierTool.ts:82`: `const confidence = isHighConfidence ? 92 : 45;`

The *threshold comparison* itself is real and config-driven (`evaluateAutonomyPolicy`'s Gate 4 does compare against `policy.minAutoConfidence`, sourced from `AgentPolicyConfig.autoThreshold`), so this isn't the literal "hardcoded `confidence > 80` inline" anti-pattern the spec's checklist warns about. But because the confidence *input* to that comparison is itself always one of 2-3 fixed constants per agent rather than a real per-decision estimate, the gate is effectively a disguised boolean (isClean/delayDetected/isEligible) rather than a genuine confidence score, undermining the "evidence-based confidence" positioning claim (`project_positioning` memory: "Qubere proves every line item").

### P1-3: `runTenderExpirySweep` is not a real Inngest function and is never called by anything
**CONFIRMED.** `apps/tms/src/inngest/tenderExpirySweep.ts:1-46` exports a plain async function `runTenderExpirySweep`. It does **not** import from the `inngest` package, does not call `inngest.createFunction(...)`, has no cron trigger definition, and uses no `step.run` (unlike the real pattern at `apps/custom/src/lib/inngest/client.ts` + `apps/custom/src/lib/inngest/functions/*`). There is no `apps/tms/src/app/api/inngest/route.ts` at all — confirmed via `find`. `inngest` is not even listed as a dependency in `apps/tms/package.json`. Repo-wide grep for `runTenderExpirySweep`/`tenderExpirySweep` outside its own file returns **zero matches** — nothing imports or calls it, no cron config (`vercel.json` doesn't exist in `apps/tms`), and no test exercises it (`apps/tms/tests/phase4.test.ts` tests quote/margin logic, not the expiry sweep).

This directly fails the spec's Phase 4 instruction ("new Inngest scheduled function (mirrors `dailyComplianceAuditJob`'s registration pattern)") and the reuse inventory's row on scheduled/event-driven jobs. `Tender.status` will never actually transition `SENT → EXPIRED` in this build; a tender that's ignored past `expiresAt` just stays `SENT` forever. Contrast with `apps/custom/src/app/api/inngest/route.ts:1-18`, which correctly registers 5 real functions with the shared `inngest` client.

### P1-4: Phase 2's "no new Movement model needed" instruction was violated
**CONFIRMED**, via `git diff packages/db/prisma/schema.prisma`. The spec's reuse inventory (Section 1) states explicitly: "No separate 'Movement' model needed — `TransportLeg` already has `sequence`, `mode`, `carrierCode`/`carrierName`... Reuse both as-is." The actual diff adds **new** `Movement` (`schema.prisma:6606-6634`), `ShipmentMovement` (`:6636-...`), and `MovementStop` models — a parallel schema to the pre-existing `TransportLeg`/`ShipmentStop` the spec said to reuse. The diff also adds a **second** carrier-profile model, `CarrierProfile` (`schema.prisma:6579-6604`), alongside the spec's requested `Carrier` model (`schema.prisma:6723-6736`) — two different, unrelated Carrier-shaped models now exist (`Carrier.legalName`/`scac`/`insuranceOnFile` vs. `CarrierProfile.party`/`scac`/`insuranceStatus`), and different parts of the app read from different ones (`carrierSelectionService.ts` vs. `apps/tms/src/app/carriers/page.tsx` querying `db.carrierProfile`). This is schema fragmentation the spec was explicit about avoiding, not a greenfield gap.

### P1-5: Exception detection thresholds are hardcoded, and one of three Phase 5 rules is missing
**CONFIRMED** (partial). `apps/tms/src/modules/tracking/exceptionDetector.ts:12`: `const ETA_DELAY_THRESHOLD_MINUTES = 120;` is a hardcoded literal, not read from any per-account config, despite the spec calling for "an account-configurable threshold" (Phase 5). ETA-delta detection (line 14) and missed-pickup-window detection (`missedPickupWindow` param) are implemented — but grep confirms `missedPickupWindow` is never actually set to `true` anywhere in the codebase (only declared/checked, never populated by a caller), so that branch is currently dead. The third Phase 5 rule, "no tracking update in N hours," has **no implementation anywhere** — confirmed via grep for `NO_TRACKING_UPDATE`/`noTrackingUpdate`/staleness-style terms, zero matches. So 1 of 3 specified detection rules (ETA delta) is live end-to-end; the other 2 are absent or unreachable.

### P1-6: Two-tier permission pattern (base action vs. risk-acceptance tier) — correctly copied for exceptions, not extended to carrier invoices
**CONFIRMED, positive finding for exceptions.** `apps/tms/src/app/api/exceptions/[id]/resolve/route.ts:1-70` correctly mirrors `apps/custom`'s pattern: base `exceptions.resolve` permission via `withAuthenticatedRoute`, plus a second `hasPermission(RISK_ACCEPTANCE_PERMISSION)` check (imported from `@qubere/decisions`) gating high-impact actions (`REROUTE`, `EXPEDITE`, `CANCEL_REBOOK`) — this is a real, working two-tier gate.

But the spec's Section 2 also calls for `carrier_invoices.override` as "the risk-acceptance tier, mirroring `exceptions.waive`... gate it the same way," for overriding a flagged invoice mismatch. `carrier_invoices.override` is registered in the permission catalog (`packages/auth/src/permissions.ts:182`) but **grep confirms it is never referenced anywhere in `apps/tms/src`** — no route checks it. A flagged `CarrierInvoice` mismatch has no code path that requires this stricter permission to override; the permission exists only in the catalog.

### P1-7: Inconsistent auth gating across routes — many skip the `permission` option, so only session-existence is checked
**CONFIRMED.** Scanning every `route.ts` under `apps/tms/src/app/api`: of the routes that do call `withAuthenticatedRoute`, more than half pass no `{ permission: ... }` option at all, e.g. `apps/tms/src/app/api/tenders/auto-dispatch/route.ts` (dispatches a real tender — a financially consequential, spec-named `tenders.send`-gated action per Section 2 — with zero permission check beyond "is logged in"), `apps/tms/src/app/api/agents/risk/sweep/route.ts`, `apps/tms/src/app/api/invoices/audit/sweep/route.ts`, `apps/tms/src/app/api/shipments/[id]/financials/route.ts`, `apps/tms/src/app/api/quotes/rfq/route.ts`, `apps/tms/src/app/api/work-items/[id]/resolve/route.ts`, `apps/tms/src/app/api/assistant/chats/route.ts` and `[id]/route.ts`, `apps/tms/src/app/api/invoices/ingest/route.ts`. `withAuthenticatedRoute`'s `options?.permission` is optional (`packages/auth/src/auth-guards.ts:99-108`), so omitting it silently downgrades the route to "any authenticated user, any permission" rather than failing loudly. This is inconsistent with the spec's validation checklist item ("Every new mutation route uses `withAuthenticatedRoute`... with an accurate `source`") which implies permission-scoped gating, not just session gating.

## P2 — minor

- `packages/assistant/src/assistantTool.ts:22-48` defines a real `AssistantToolRegistry` class with `.register()`/`.get()`/`.execute()`, but `apps/tms/src/modules/assistant/orchestrator.ts` never uses it — it calls `availableAssistantTools.run_risk_sweep.execute(...)` directly against a plain object export in `apps/tms/src/modules/assistant/tools.ts`. The registry abstraction is dead code in apps/tms today.
- `TransportationOrder` (`schema.prisma:6524-6568`) has duplicated/overlapping fields not in the spec's model definition: both `origin`/`destination` and `originAddress`/`destinationAddress`, both `weight` and `totalWeight`. Not incorrect, just schema noise versus the spec's leaner definition.
- `apps/tms/.env.local` contains a live-looking Supabase `DATABASE_URL` with an embedded password in cleartext, committed to a tracked `.env.local` file rather than being Vercel-project-env-only. Outside this audit's core scope but worth a follow-up since it's a real credential sitting in a file that can end up in a diff.
- `apps/tms/tests/phase4.test.ts` covers quote/margin logic (spec's Phase 3 content) but nothing under the `phase4.test.ts` name exercises `runTenderExpirySweep`, tender status transitions, or the auto-dispatch fallback cascade — the phase-numbered test files don't line up 1:1 with the spec's phase numbering, making "which phase is actually tested" hard to audit from file names alone.

## Summary table

| Area | Verdict |
|---|---|
| Inngest functions | 1 file exists, is not a real Inngest function (no `createFunction`, no cron, no `inngest` dependency), has zero callers, and is not registered anywhere. Tender expiry never actually happens. |

| modules/agents, modules/autonomy | One file each. Both contain real, non-trivial deterministic logic (3 agent functions; 1 policy engine) — not empty stubs. Genuinely the most solid part of the build. |
| Exception detection (Phase 5) | 1 of 3 specified rules (ETA delta) is live; missed-pickup-window is coded but never triggered; no-tracking-update-in-N-hours doesn't exist. Two-tier permission pattern correctly copied for exceptions; not extended to carrier-invoice override. |

But the webhook has no auth/signature verification and no tenant scoping (cross-tenant IDOR). Two separate "live tracking" files fabricate named-vendor data and are currently unwired dead code. |
| LLM call sites | Zero. No SDK, no dependency, no API key. The chat "AI assistant," "AI document parsing," and "AI email intake" are all hardcoded/heuristic/pass-through code with no model call anywhere in the request path. |

**Is this actually agentic, or a UI shell over static/hardcoded data?** Mostly the latter on the "AI" surfaces a demo would lead with (chat, document parsing, email intake), but there is real deterministic agent logic underneath for rate scoring, invoice auditing, and risk sweeps, gated by a genuinely config-driven (if partially unused) autonomy policy engine — so it's not *all* shell, but nothing in this build understands unstructured input the way "AI Freight Execution" implies, and a customer who tests the document-parsing or email-intake screens with their own real documents will get back fabricated data that has nothing to do with what they uploaded.
